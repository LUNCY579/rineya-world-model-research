# Operational planning and narrow retention audits

Frozen instrument intent before native planning/retention measurements. These
are exploratory development measurements, not the G5 co-primary study.

`planning_evaluate.py` takes the first at most two independent register dev
parents whose four-action generated goal is exactly 3–4 optimal legal moves
away. The current 24-row dev bank has ONE eligible parent. Goal and optimum
construction use exact rules before learned outputs; the planner receives only
the initial state/rules/goal and a static action syntax library. No source plan
or exact legality filter is available in search. Freeze the serialized input
snapshot and script hash before model loading. Beam width1, depth4, max20
transition queries and120,000 cache-disabled decoder token positions per
episode. Same caps apply to every arm. Costs below the cap can differ and must
be reported. Only after final choice does the exact scorer check success and
all actions' legality. This one-parent register screen cannot establish hard
planning generalization, cross-domain transfer or a primary P2 effect.

`audit_retention.py` freezes six new fixed one-step fixtures in the old BWM
RegisterWorld and RCWM ledger prompt formats BEFORE loading the parent/adapter.
No historical evaluation-bank row is read. Compare core and each adapter on
the identical response tokens, including EOS, using teacher-forced chunked CE.
Token-weighted per-domain and overall differences are diagnostic. They are NOT
behavioral retention measurements, the 375-item guard, a noninferiority test,
or a retention pass. `retention_pass` remains null. Changes in loss require
careful follow-up, not a claim of preserved skills.

All new scripts record their source/fixture hashes. Original training and
evaluation freezes remain append-only; auxiliary audit scripts do not alter
the fixed dynamics instruments or expose confirmation labels.
