# Next-domain pilot audit: registered Ledger-world warm start

Date: 2026-10-12, America/Chicago. Read-only source/metadata audit; no native model was loaded and no historical evaluation row, sealed label or test plan was accessed. The design below is a proposed development pilot, not a preregistered or executed result.

## Recommendation

Use **Ledger-world initialized from RCWM T2 seed0** as the smallest useful second domain. It has a compact four-integer reply, an established canonical one-step interface, a known four-step error channel, and no Blocksworld deletion-support check masking model legality errors. Start with a fresh B0 interface qualification; then, only if qualified and resources permit, run the same small A0/A1/A2/A5 objective matrix from identical unmerged T2 bytes. This tests transfer of the implementation beyond RegisterWorld without claiming broad world-model efficacy.

Keep Blocksworld as a later relational test. Its raw legality and parser-support contributions need separate measurements; the inherited one-step model is already near its accepted-state ceiling on logged historical search queries. The current <=5-object parent canonicalizer also makes a large independent-parent tiny-Blocksworld collection impossible: valid initial configurations modulo renaming have p(n)+p(n-1) forms (table tower partitions plus one held block), giving5,8,12 parents at3,4,5 blocks—25 total. Do not copy the128-train/24-dev RegisterWorld quota into that finite state pool and silently count renamed duplicates as independent parents. A larger block count/parent definition requires an explicit new canonicalization/split protocol.

## Exact interface and the tick compatibility hazard

For canonical one-step prediction use `rcwmt.env.one_step_messages('ledger_replay', before, event)` and the verified non-thinking Titan chat template. For direct horizons2/4 use `multi_step_messages` on the initial balances and ordered event prefix. Model inputs contain no intermediate states, outcome labels or goals. Primary four-step evaluation chains the original one-event interface on each previous **predicted** state.

Canonical state is exactly `{"A": int,"B": int,"C": int,"D": int}`. Each valid event has exactly six keys: `account, amount, kind, other, status, tick`, with kinds add/scale/transfer, integer amount/tick, A-D account references, and other!=account for the initial canonical contract. The model reply is **bare balances** with exactly the same four keys. Do not require the generic DSv3WM `{state,legal,terminated,failed}` reply from this existing adapter. Use strict full JSON, integer-not-boolean values and duplicate-key rejection; report that parser tightening against the old lenient historical parser.

**Important implementation hazard:** frozen `dsv3wm/domains.py:98` allows only five ledger event keys and rejects `tick`. Sending a canonical six-field event through its current `exact_transition`/`make_record` path labels it an illegal no-op. A new standalone collection adapter must validate six-field inputs and call the read-only `rcwmt.env.step`, or explicitly strip neutral tick for execution while retaining it in the prompt. Preserve frozen domains.py; never silently generate these wrong labels.

The generic `planning.action_library` also emits five-field events without tick. A future Ledger planning adapter must use a prospectively fixed six-field static library. Ordinary structural `data.load_records` remains usable, but do not invoke generic `validate_record(verify_labels=True)` for these six-field trajectories; replay through the dedicated Ledger collector instead.

Ledger has no dynamic precondition/termination predicate for valid events: posted events apply add/scale/transfer; any other status is a **legal no-op**. Tick is causally inert. An input-structure wrapper may derive legal=true/terminated=false/failed=false for valid streams, but these are **known contract flags**, not learned legality/termination accuracy. Unknown/malformed events belong in a separately documented wrapper extension. The original reply does not predict flags.

Posted operations must change state, no-op statuses must not, and every primary four-step final state must differ from its start, preventing an all-copy final-state floor.

## Retention and implementation boundaries

New ledger training must retain add/scale/transfer and no-op cases rather than optimize only one operation. The joint control-skill rule (RCWM D-49/BWM X-04) applies to every operation an active adapter must keep. T2 also contains modulo97-register/prerequisite adaptations: if the new adapter is expected to serve those families, add fresh controls for all their operations and measure their behavior against T2 B0. Otherwise keep the child adapter strictly ledger-scoped, preserve original T2 for other uses, and still disclose unmeasured cross-family behavior. Never claim retained general skill from lower token loss alone.

The current Config target modes and generic data target projection are incompatible with bare balances; add a separate Ledger module/CLI rather than edit frozen recovery/objective/data files.
