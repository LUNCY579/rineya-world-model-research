## Resolver and manifest semantics

V4 `:32–36` publishes the **required minimum** of a resolved inherited entry: `name,scope,source_family_key,auxiliary_scalar_variant,observation_length,control_id,pair_sample_ids,exact_candidate_sha256`, plus actual parsed comparison/prefix evidence. The existing `supplied_same_table_v2_pairs` collection may be retained. Neither its name nor a closed top-level/entry object schema is made mandatory by that paragraph. Implementing such a closed schema without a NEW public amendment would introduce an unpublished criterion.

Resolve an actual repository-relative manifest path bound in the execution receipt, then match the exact claim `control_id` + normalized public identifier + ordered actual pair. Check every matching entry's required fields against actual resolved records and the exact complete candidate bytes. An ID alone, generic family label, matching annotation, or stored producer target is insufficient. Two entries with different public names may share one truthful pair/control ID. No global evidence-ID uniqueness or regex/ID-spelling rule exists. Inline pair IDs disambiguate other explicitly mapped pairs; report identical duplicate evidence without inflating corpus/pair counts. Conflicting matching entries are errors, rather than silently choosing one.

The exact candidate hash and actual record resolution can bind custody. Recompute actual canonical record hashes using the existing canonical contract and report resolved row/task/prompt hashes in the checker receipt. Do **not** require a new producer `pair_record_hashes` field, manifest self-hash in each claim, private producer report, or a new section. Candidate-to-manifest paths and manifest-to-candidate hashes avoid a circular embedded-hash requirement; the external execution receipt binds both exact byte streams. Optional descriptive fields and independently derived extra measurements are not newly mandatory gates. False factual evidence must not be trusted, but an unspecified measurement-key encoding should be recorded as UNKNOWN/unsupported pending publication, not invented as a false semantic property.

## Matched claimant recommendation and remaining clarification

The recommended simple revision attaches two inherited claim objects per row, sharing that row's coordinate-matched physical witness: length2 rows nominate E/G and length3 rows F/H, in the same family/variant/schedule/style. All eight contexts remain valid claimants; a nonmember's pair need not contain its own ID. Its actual worlds/queries match the pair's coordinate group, but its observations, prefix sets, final status and row properties need not match E/F.

V4 `:18` definitely matches the coordinates **between pair members** and allows nonmembers. V4 `:20` calls the claimant-coordinate mapping the “simplest” encoding and a “recommendation.” If rejecting a nonmember's different-length or other-coordinate same-family truthful family witness is intended to be a hard gate, publish a NEW small prospective encoding supplement explicitly requiring the claimant's length/variant/schedule/style to match. Do not silently infer that extra restriction from the mere existence meaning of a family claim. The hand demonstration has separate minimum-V4 and recommended-matched-owner modes to expose this boundary.

The same applies to closing manifest/evidence object keys: before requiring an exact producer comparison/prefix shape, publish that shape and how duplicates/optional evidence are handled. Alternatively implement the published minimum with input-derived complete proof recorded by the checker, without asserting an unpublished annotation schema. Existing field-order pair equality and conditional crossing remain required; no new shared-key ordering fingerprint or ID-based style inference is recommended.
