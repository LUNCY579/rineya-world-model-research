## Supplied controls and exact ordered members

Each of the following is a family relation with scope `corpus_variant`. These public names identify the existing control meanings; name and property use the same string.

| Name/property | Ordered contexts | Required independently derived relationship |
|---|---|---|
| `uninterrupted_resume_suffix` | F,R | Same program/root request and original initial state. R carries an actual nonterminal committed prefix and its exact normalized checkpoint. R completes with F's terminal state/status and exact remaining event suffix. At least one effect is already committed and future work remains. |
| `resume_restart_replay` | R,T | Only mode changes. Both validate the same original history/checkpoint. Restart root initiation passes, and an actual committed non-idempotent effect occurs again. Continuation traces differ and terminal state or status differs. Recompute the repeated effect from both actual traces; a blocked restart does not satisfy this relation. |
| `budget_pause_after_effect` | R,P | Only event_budget changes. P's positive budget creates a second still-running checkpoint after at least one new effect and leaves pending work. P's new events are an exact prefix of R's new events. |
| `second_checkpoint_suffix` | P,U | U resumes the exact second checkpoint and the original history extended by P's new events. Program/root request/initial state remain fixed. U's completion reproduces the same uninterrupted F suffix, terminal state and status; no committed effect repeats. U uses the configured full continuation budget. |
| `positive_bound_argument_counterfactual` | F,A | Only one root argument expression changes. Both runs initiate and complete. An actually used bound parameter changes a later effect, guard or success computation, producing a different actual event trace or outcome. A declared but unused parameter is insufficient. |
| `initiation_argument_counterfactual` | F,I | Only one root argument expression changes a decisive root initiation atom. F initiates; I fails initiation with zero effects. All other program, state and request fields remain equal. |

| `object_field_order_invariance` | Same context forward,reverse | Exact typed task, target and list-order equality after decoding. Only recursive object-field presentation differs. |

The first eight controls require both members to have the same actual source family, index, split and renderer. A record in any context may own those family claims without belonging to their pairs. Pair coordinates must match that owner's actual family/index/renderer. The field-order claim is the owner's own context pair, ordered forward then reverse; the owner may be either member. Every context and renderer must resolve from actual records. Do not parse a private sample-ID syntax to obtain coordinates.

Each candidate record carries exactly these nine supplied claims. Each claim has exactly `name`, `property`, `scope`, `evidence_manifest`, `control_id`, and ordered `pair_sample_ids`. `name=property` is a name from the table, `scope=corpus_variant`, and `pair_sample_ids` contains two distinct actual candidate sample IDs in the published order. The evidence manifest is a safe factory-relative path to the supplied control manifest. No claim contains a target or a per-row expected status. Claims owned by nonmembers express a family relation, with no implied individual outcome.
