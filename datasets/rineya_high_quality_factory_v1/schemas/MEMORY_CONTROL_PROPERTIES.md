# Public factual properties for the REM delayed-history gap

Design version: REM-GAP-003, 2026-10-09. Actual author: `/root/research_architect`, Dataset Research Architect. These definitions supplement the existing `kind=episodic` contract in `EXTENDED_SEMANTICS.md`; they change no input/output semantics and supply no candidate gold labels. A property is a falsifiable coverage claim, not an efficacy claim.

## Shared definitions

For a query q, eligible events have its exact key and `at <= q.as_of`. The winner W(q) maximizes `(version, at, zero_based_input_event_index)`. Let A(q) be the **semantic answer** `(status, typed value)`, distinguishing null, boolean, integer and string; in particular true differs from integer 1, and present-null differs from absent-null and deleted-null. Version and event index remain required exact outputs, but a change in either alone is not a decisive answer change. Let A(e) mean the status/typed value that selecting event e would produce. A hypothetical incorrect resolver mentioned below is solely a diagnostic control, not an alternative valid answer.

Per-record tags below require witnesses **inside that record's visible task**. Related sibling records cannot establish a per-record tag. A witness identifies query signatures `(key,as_of)`, event indices, applicable tuple comparisons and semantic equality/inequality, with independently derived answers. Witnesses belong in audit evidence, not in the student prompt. All queries remain independent; no query result feeds another query.

## Per-record property names

| Property | Exact witness required |
|---|---|
| `decisive_delayed_boundary` | There is an integer T >= 1 and two queries for the same key at T-1 and T. An event with `at=T` is W at T, and A(before) differs from A(at). Thus the newly eligible event changes status or typed value at the exact boundary. Arbitrary long gaps, an unqueried update, and provenance-only changes do not qualify. |
| `version_over_recency` | For a query, W has higher version and earlier timestamp than an eligible same-key competitor. Selecting solely by latest `(at,index)` among eligible same-key events would give a different A. This demonstrates an actual conflict between version priority and recency, rather than merely the presence of a lower-version event. |
| `equal_version_time_conflict` | For a query, at least two eligible same-key events at the maximum eligible version have different timestamps and different A(e); W has the latest timestamp. At least one older top-version competitor has A(e) different from A(W). Lower-version disputes alone do not qualify. |
| `equal_version_time_input_conflict` | For a query, at least two eligible same-key events share the maximum eligible `(version,at)` and disagree in A(e). W has the largest input index, and at least one other event at that same top tuple has a different A(e). An inactive tie elsewhere in history does not qualify. |
| `authoritative_tombstone` | For a query, W is delete and an eligible same-key put with lower version exists. The lower-version put cannot revive the key. The stronger recency challenge is separately certified by `version_over_recency` if its witness also holds. A delete with no eligible competing put does not certify this conflict property. |
| `present_null_distinction` | The task has a query whose W is put-null, and a query with absent or deleted status and null value. Their statuses differ although their values are null. Put-null alone does not certify a distinction control. |
| `future_event_filter_control` | For a query, an event with the exact key and `at > as_of` would win the tuple if the cutoff were ignored. Its A(e) differs from the actual A(q), including the case where q is absent. Thus ignoring time eligibility changes the answer. A future event that would still lose does not qualify. |
| `cross_key_filter_control` | For a query, maximizing the declared tuple over **all keys** with `at <= as_of` selects an other-key event whose A(e) differs from A(q). The exact-key filter therefore prevents an observable wrong answer. Mere unrelated context does not qualify. |
| `absence_control` | A query has no eligible exact-key event. Audit evidence classifies whether the key has no events anywhere, or only future events. This certifies contract-defined absence, not unresolved conflict or epistemic uncertainty. |

Only properties actually witnessed may be tagged. A valid row can have fewer properties than its family. If an audit reports counts for missing-key absence and future-only absence, keep them separate. A future-only absent query may also witness `future_event_filter_control`.

## Family controls, distinct from per-record tags

The following names describe **relationships among supplied variants**, or documented audit probes. Report the scope explicitly as `corpus_variant` or `audit_probe`. A hypothetical transformation that was never instantiated is not supplied corpus coverage. Audit probes add zero source families and zero training records.

| Family control | Required matched evidence |
|---|---|
| `query_role_id_position_crossing` | Declare eight query roles and an exact eight-rotation schedule per controlled history. Every underlying role/signature occupies every one of the eight reused IDs and every input/output slot once per field-order style. Derive actual status, present-null and value-type histograms per ID and position. Each ID/position must have the identical role and outcome histogram within the complete rotation set. Query ID and position may remain coupled; this control does not claim their mutual independence. |
| `key_role_crossing` | Declare four semantic key groups and an exact within-family assignment table identifying history, query-rotation and field-order indices. Each of the same four equally styled key strings occupies each group an equal number of times in the stated complete schedule. Crossing can occur over four controlled histories, or within each history's eight rotations, or another exactly balanced declared schedule; it need not occur specifically between histories. An eight-rotation crossing over four groups gives each key/group pair twice per history per field order. Queries and events must be renamed consistently in each variant. Report actual role, status and type histograms for each key string after the full set; show equality for semantic isomorphs, or disclose measured residual differences when control histories are not isomorphic. Query rotation alone, without a consistent event/query key reassignment, does not cross key roles. Shuffling names without these measurements does not certify shortcut removal. |
| `field_order_invariance` | Two renderings have identical parsed event order, query order, scalar types and values, and differ only in JSON object field order. Exact typed outputs agree. Reordering the event list is excluded because an active index tie can change the answer. |
| `lower_version_append_invariance` | For explicitly named protected queries with an existing winner, append eligible same-key competitors whose versions are strictly below each protected query's winning version. Preserve every old event index. A(q), chosen version and chosen event stay unchanged for those queries. Do not generalize to earlier absent queries for which an append could create the first eligible event. |
| `other_key_edit_invariance` | Hold the protected queries and all their exact-key events fixed; modify only other-key events. A(q) and selected event identity stay unchanged. If an edit shifts indices, compare decoded winning event identity and recompute its new required index, rather than incorrectly demanding unchanged numeric provenance. |
| `future_event_edit_invariance` | For the named protected cutoff/query, modify only events strictly after that cutoff. A(q) and selected event identity stay unchanged; account for index shifts as above. The edited events may matter to other later queries, which are not covered by this control. |
| `version_priority_counterfactual` | Hold a query/history fixed except the version of an eligible same-key competitor whose A(e) differs from A(q). Raise that version above all eligible same-key versions. It becomes W and A(q) changes. Report the changed field and old/new tuple relations. |
| `active_input_tie_swap_counterfactual` | Hold a query and all event fields fixed and swap only two conflicting events at the active top `(version,at)` tie, including the former winner. The swap makes a conflicting event the new largest-index top-tuple event, so A(q) changes. Swapping an inactive pair does not qualify. |
| `null_lifecycle_counterfactual` | At a winning event with null value, change only op between put and delete. Keep history order, key, version, time, query and null value fixed. Status changes between present and deleted while value remains null. |
| `query_key_counterfactual` | Hold the history and cutoff fixed, change only the queried key, and witness a changed A(q), including a no-eligible-event control when supplied. A rename applied consistently to history and query instead is semantic invariance, not this counterfactual. |

For any added `temporary_delayed_winner` claim, require same-key queries at T-1, T, U-1 and U, with T >= 1 and U >= T+2. The event at T wins at T and U-1, the successor at U wins at U, and both boundary comparisons change A. A successor occurring too soon to provide the required query interval, or an unqueried transient winner, does not qualify. This is optional extra coverage beyond the eight-role pilot; do not infer it from history length.

## Required shortcut and count report

The proposed pilot has **12 source families x 4 controlled histories x 8 query rotations x 2 field orders = 768 correlated records**. That is 48 base controlled histories before any consistently renamed key-role views, not 768 independent worlds. Key-role crossing may use the same eight rotation variants rather than adding a new multiplier. The plan has eight queries per row; assuming eight distinct signatures per base history after decoding consistent key renames, it supplies 384 base history/query observations, 3,072 rotation-level observations and 6,144 rendered observations. Verify uniqueness and report actual counts rather than copying these planned numbers into an achieved-coverage report.

All variants and probes retain their source family's split. Report full counts and source-family counts separately. For each family and each history, publish role-by-ID and role-by-position crossing tables; publish status/type/present-null tables by ID, position and key string. Each base history should include present, deleted and absent queries, so every reused ID/slot sees all three after a complete rotation set. Distinguish positive support from equal class frequency: the rotation can equalize histograms across nuisance buckets while the overall status classes remain imbalanced. A key-role schedule alone is insufficient if actual per-key label histograms still expose a shortcut; disclose or correct that residual before making a removal claim. Keep meaningful timestamp/version correlations distinct from arbitrary-name/position leakage.

Per-row witness coverage, family crossings, paired control coverage, and any remaining conditional label correlations are separate acceptance checks. Correct gold does not excuse a false property tag. No property certifies persistent learned memory, semantic/associative relevance, source trust, an unresolved-conflict policy, multi-query composition, or model robustness. Those require additional public semantics and separate evidence.
