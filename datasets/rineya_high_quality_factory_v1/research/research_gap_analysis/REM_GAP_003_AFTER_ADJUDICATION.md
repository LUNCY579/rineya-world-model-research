The next small gap should prioritize actual unsupported behavior over another rendering multiplier:

1. **Future-only absence with exact cutoff boundaries.** Current absent queries all use keys with no events anywhere. Add matched same-history/same-key queries just before and at the first event; before must be absent and at must change status or typed value. Cross first put, put-null and delete when the public contract permits them. Separate the missing-key and future-only subtype counts, preserve eligibility/precedence details and measure outcome support across nuisance buckets. Current future-filter controls on already-populated keys do not cover this subtype.

2. **Cross joint nuisance schedules and semantic partial-label strata.** Marginal full-outcome histograms already match across ID, position and key. Own joint empirical status majority fractions still reach 0.875. Use independently controlled ID/position/key schedules when joint independence becomes a stated goal. Vary same-key event multiplicity within status/type strata, rather than merely adding other-key filler: exposed dev event-count lookup reaches 84.375% status accuracy but 12.5% exact core accuracy. Evaluate exact answers and targeted property subsets together; a wrong version-then-index resolver can look strong in aggregate while failing time-priority controls. These are dataset diagnostics, not trained-model accuracy.

3. **Add genuinely different order-invariant history relationships.** The broader adversarial normalization finds nine relation motifs, six shared across train/dev. New timestamps, names and shuffled precedence groups do not establish a new mechanism. A small next pilot could vary repeated delete/revive chains, transient updates with queries before and after each exact boundary, competing eligible-version strata and typed values while maintaining independent source-family custody. Count decisive answer changes and active competitors; extra history length alone is insufficient. Familiar max-tuple semantics and exposed development remain limitations.

4. **Specify new semantics before claiming deeper memory.** Multi-record relevance rules, dependent read/write queries, unresolved conflict/abstention, retrieved procedures and protected postconditions would require separately stated public contracts and independent oracles. Query joins or chained writes must demonstrably affect later requested answers. Status/typed-value counterfactuals should isolate which input fact causes the answer change. The current eight queries are independent argmax computations, so this pilot cannot establish those competencies or higher curriculum levels.

5. **Separate data coverage from system outcomes.** Persistent memory, learned write policies, forgetting reduction and efficacy require separate authorized model/system work. This note neither opens protected instruments nor proposes reusing exposed development as a sealed evaluation. Actual independent agent executions and guided corrective review are disclosed; shared underlying-model errors remain possible.
