# GitHub archive and local eviction policy

On 11 October 2026 the user explicitly requested that GCDL-001 datasets, relevant evidence and records be saved and verified on GitHub, then removed from local storage, and that this process recur whenever storage is tight. The user confirmed that this authorization applies to **GCDL-001 only**. This instruction supersedes the earlier rule against deleting verified backed-up local accepted payloads. Remote accepted bytes, IDs, labels, configuration identities and sealed instruments remain immutable.

The approved archiver must first commit and push unchanged payloads and a catalog to `LUNCY579/rineya-world-model-research`, then create an immutable `archive/gcdl-001/<commit>` snapshot reference. Before local unlink, it verifies the snapshot reference, catalog, Git tree path, blob identity, complete returned bytes, byte length and SHA-256. It rechecks every local file and its identity under the worker lock. Verification, transport, path, hardlink, race or custody failure preserves unverified local files; partial verified eviction remains recoverable through the durable index.

Eligible payloads include accepted/sealed/quarantined datasets, completed rendered datasets, historical reports and immutable runtime snapshots. Runtime snapshots use SQLite's consistent backup API under the worker lock. A remotely verified copy of the retired development archive must precede removal of its original ignored local payload.

Only lightweight operational controls remain local: executable code and configurations, approval and policy controls, canonical manifests/protected split indices, the live minimal queue/checkpoint database, STOP/PAUSED/lock files, and the remote archive index. They contain no accepted target trajectories. Live control files are never eviction candidates. Archived payloads are fetched only into bounded process memory when an explicit audit or nonsealed export needs them; no persistent raw cache is allowed. Producer recovery uses sealed hash/index metadata, without decoding sealed answers. A full sealed audit is a separate explicit auditor action.

Once the archive snapshot is verified, the active research branch may remove archived payloads from its current tree while the immutable snapshot retains them on GitHub. The backup guard must reject any deletion lacking verified snapshot custody. Rebuilding the owned Git store as a shallow, single-branch, blobless checkout removes residual local payload objects; archived blob IDs must be absent from its object inventory. All redundant owned proposal/store copies must also be removed after preservation checks.

The five-minute worker checks this policy when actual free space falls below the existing 10 GiB floor. A disk-only paused invocation may archive verified payloads but preserves the pause. Operator STOP and unresolved quality, backup or migration pauses remain binding. The quiet scheduled follow-up rechecks space and may resume a disk-only pause only when every resource, reviewed-source, queue and integrity gate passes. No generation gate is relaxed, and eviction cannot guarantee sufficient space when other programmes consume the host disk.

This policy is authorization and a design contract. Its implementation requires independent review and regression/custody tests before production eviction. No other Rineya programme, agent-owned files, global authentication, main branch, paid API or model-training operation is authorized.

Keep current quality controls compact and bind them to the current reviewed-source and archive-index digests. Detailed historical reports stay cold. Explicit full audits may return detailed results in RAM; store only the necessary current verdict/count/gate control locally, so a historical report blob is not recreated as an active control alias.
