# Bounded recovery after GitHub eviction

The second resumed production cycle preserved six new canonical batches (188 records) and twelve rendered source-group exports (1,488 derived rows), then hit the unchanged 340-second watchdog just before publishing a healthy heartbeat. Totals at its durable checkpoint were 2,528 accepted records and 2,976 derived rows, with no quarantine. The checkpoint and timeout evidence are retained. Qualified backup confirmed these new payloads at commit 228a243d58ddb018a8fa04ac2f8bdb16bcf5d861 before any local eviction.

The timestamps place approximately 196 seconds of approval/cold recovery before the first generation step, about 114 seconds from generation completion through rendering, and about eleven seconds of final summary work. Backup was not due: its prior confirmation was less than the configured thirty-minute interval before timeout. Launchd sends stdout/stderr to /dev/null, so the request-by-request timing explanation is an inference from checkpoints/events and the executable path, not a captured network trace.

Each default cold read previously created its own authenticated transport and fetched catalogue/commit/tree metadata anew. The proposal adds a cycle-scoped, root-bound RAM read session with bounded metadata caches. Verified raw bytes remain under the existing sixteen-MiB RAM LRU; no payload or raw Git object is restored to disk. Every newly fetched cold payload still checks its snapshot reference before and after reading, verifies the committed path/OID/length and full blob identity/SHA256, and authenticates the exact catalogue. Mutable local index/control validation remains fresh. Cached reading metadata never substitutes for the separate fresh destructive custody proof used by eviction.

The fake transport tests measure twelve small cold manifests at 132 API calls/twelve owner-auth calls before sharing, versus44 API calls/one auth call with sharing. Both execute24 fresh reference checks. This establishes request reuse, not actual host throughput. Cache limits, corruption, changed/missing refs, changed index, caller deadlines, nested root/deadline isolation, falsey explicit providers and absent payload materialization are tested separately.

The production clock now begins before approval and recovery. Normal publication uses the existing 144-second work window inside the configured180-second processing budget. Only completed, verified processing may enter the existing140-second final backup/approval reservation; the total320-second bound remains below the unchanged340-second watchdog. Natural time exhaustion checkpoints and yields for the next invocation. Actual source, custody, quality and backup failures still pause. No healthy heartbeat is emitted after expiry.

Rendered export checks the deadline between records/views. A partial export retains its bytes and remains pending until every required view and its immutable batch receipt verify. Replay reproduces existing view bytes exactly. A completed archive operation yields before opening the production database or generating more data, avoiding combined archive-plus-production watchdog overruns. Existing disk/operator/quality/migration pause semantics remain binding.

The candidate does not alter generator profiles, configurations, mathematical environments, old accepted bytes/IDs/labels, frozen sealed evaluation or candidate-selection semantics. Actual deployment, bounded cold-cycle completion and archival cleanup require the final independent source approval and recorded live receipts; focused test results alone do not assert those outcomes.
